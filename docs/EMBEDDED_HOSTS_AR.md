# WolFox — الأيقونة داخل أي تطبيق تدمج فيه الموديول

## ما تغير

هذه نسخة **Embedded Hosts** مستقلة من QA2. أُزيل شرط اسم الحزمة الوحيد من نقطة دخول WolFoxHook، وأصبحت أسماء تطبيقات Android الصالحة مؤهلة عند دمج الموديول أو تحميله داخلها بإذن صاحب التطبيق. لم تتغير الألوان والخط والإغلاق السفلي والبحث وحفظ الموقع الدقيق أو شروط التفعيل والإخفاء.

قائمة `scope` في بيانات الموديول أصبحت فارغة **كتلميح نطاق غير مقصور على تطبيق واحد**، وليست wildcard أو أمرًا لدمج الموديول في كل التطبيقات. تحديد المضيف وتحميل الموديول مسؤولية مشروعك/إطار التحميل. قد يحتاج إطارك تحديد التطبيق أو النطاق في إعداداته صراحة.

تستثني السياسة حزمة Android الأساسية وSystemUI والموديول نفسه وأسماء الحزم غير الصالحة. لا تُعدّل APKs خارجية، ولا تُحمَّل ملفات أي تطبيق غير مدمج أو غير مختار.

fallback دورة Activity لم يعد يفترض أن اسم عملية المضيف يساوي اسم حزمته؛ يمكن أن توجد واجهته في عملية مخصصة. لا يُظهر ذلك الأيقونة تلقائيًا: لا بد من طلب إظهار داخل Activity فعلية.

## المقصود بـ«داخل أي تطبيق»

الأيقونة View داخل `android.R.id.content` الخاص بـActivity في التطبيق المضيف. لا تظهر فوق تطبيقات أخرى لم تدمج فيها الموديول، ولا تستخدم SYSTEM_ALERT_WINDOW أو Accessibility service أو خدمة Overlay أو تشغيلًا عند الإقلاع. لا تحتاج صلاحية «الظهور فوق التطبيقات» لهذه الطريقة.

تثبيت APK الموديول وحده لا يدمجه في التطبيقات. يجب أن يضيف مشروعك الشيفرة والأصول، أو أن يحمّل إطار hooks متوافق الموديول داخل تطبيقك المصرّح به. لم نعدّل أو ندمج أي APK مضيف خلال هذا التسليم.

## دمج مباشر في مصدر تطبيقك

استخدم مصادر `app/src/main/java/com/wolfox/gps` والأصول من `app/src/main/assets`، مع اعتماد Xposed API للتجميع فقط عند تجميع كامل المصدر. احتفظ بملفات الأيقونة وHTML والخطوط بنفس المسارات؛ فهي جزء من التصميم والخريطة. لا تضف stubs أو Xposed API إلى runtime على أنها بديل لإطار hooks.

الأصول المطلوبة في المضيف عند نقل المصدر:

```text
assets/wolfox_icon.png
assets/wolfox_map.html
assets/wolfox/fonts/DINNextLTArabic-Medium.ttf
assets/wolfox/fonts/DINNextLTArabic-Regular.otf
```

اربط دورة الحياة في Activity الخاصة بك:

```java
import android.os.Bundle;
import android.view.MotionEvent;
import com.wolfox.gps.DirectBootstrap;

@Override
protected void onCreate(Bundle savedInstanceState) {
    super.onCreate(savedInstanceState);
    // جهّز شاشة التطبيق المعتادة أولًا، ثم اربط الموديول.
    DirectBootstrap.attach(this);
}

@Override
public boolean dispatchTouchEvent(MotionEvent event) {
    DirectBootstrap.observeTouch(this, event);
    return super.dispatchTouchEvent(event);
}
```

`attach` يسجّل مراقبة دورة الحياة ولا يطلب الإظهار. عند الربط المباشر تستغني دورة الحياة عن fallback المكرر، بينما observeTouch يراقب ضغط المنتصف دون استهلاك لمس التطبيق. أضف attach للواجهات التي قد تكون أول نقطة تشغيل إذا لم تكن لها Activity أساسية مشتركة؛ التسجيل نفسه محمي من التكرار.

**لا تستدعِ showControls تلقائيًا من onCreate/onResume** إذا أردت الحفاظ على الإخفاء الافتراضي. استدعِ أمر الإظهار من إجراء مستخدم واضح فقط:

```java
// داخل listener لزر/قائمة إظهار، لا عند بدء التطبيق تلقائيًا:
DirectBootstrap.showControls(activity);

// عند طلب الإخفاء:
DirectBootstrap.hideControls(activity);
```

أو اضغط مطولًا **850ms في منتصف شاشة المضيف** للإظهار، ثم اضغط الأيقونة لفتح اللوحة. إذا لم يتوفر ترخيص صالح تُفتح شاشة التفعيل وفق السياسة الأصلية. الضغط المطوّل على الأيقونة وخيار الإخفاء يحافظان على الإخفاء. بعد إعادة تشغيل عملية المضيف لا تعود الأيقونة حتى طلب جديد.

يمكن استخدام نفس أوامر attach/show/hide مع أسماء تطبيقات مختلفة؛ لا يلزم تعديل ثابت package داخل WolFoxHook لكل مشروع. بيانات الحالة محفوظة داخل المضيف، ولا تنقل بيانات التفعيل أو سجل المواقع تلقائيًا إلى تطبيق آخر.

## التحميل عبر إطار hooks

إذا كان إطارك يحمّل الموديول ويفعّل ActivityHook داخل التطبيق، فـfallback دورة الحياة ورصد الضغط المطوّل موجودان. نقطة الدخول:

```text
com.wolfox.gps.hook.WolFoxHook
```

واجهات DirectBootstrap العامة محفوظة من تغيير الاسم أثناء R8. لا تحمّل نسختين مستقلتين من الموديول داخل classloaders مختلفة؛ اختر طريقة تكامل واحدة واضحة. مصدر الموديول وحده لا يثبت أن إطار التحميل الحالي يدعمه أو أن native/isolated process تُحمّل الوحدة فيه.

## الظهور والتزييف ليسا الشيء نفسه

ظهور الأيقونة داخليًا لا يعني نجاح محرك GPS. التزييف يحتاج إطار hooks فعليًا محمّلًا في عملية المضيف، وموقعًا صالحًا وترخيصًا فعالًا واستجابة فحص runtime. لا تُخفى علامة Mock ولا يُفتح مسار TestProvider أو Root أو خيارات مطوّر. الكود لا يغير GPS للنظام أو التطبيقات غير المدمجة.

بوابة الاشتراك والانتهاء والحظر الإداري بقيت كما هي. توسيع أسماء المضيفات لا يلغي القيود التي قد يطبقها خادم التفعيل أو شروط صاحب الترخيص. أذونات الإنترنت والموقع الأصلية تحتاج وجودها في Manifest المضيف عند دمج المصدر، مع طلب الإذن وقت التشغيل عند استخدام الموقع الحقيقي؛ لم تُضف أذونات ظهور عامة.

## البناء والتحقق

نسخة APK تسلّم بتوقيع اختبار؛ source وGradle Wrapper وverify-qa موجودة. استخدم Java 17 وSDK 34 وBuild Tools 34.0.0، وXposed API 82 الرسمي اعتماد تجميع فقط:

```bash
export JAVA_HOME=/path/to/java17
export ANDROID_SDK_ROOT=/path/to/android-sdk
export ANDROID_BUILD_TOOLS="$ANDROID_SDK_ROOT/build-tools/34.0.0"
export XPOSED_API_JAR=/path/to/official/xposed-api-82.jar
export WOLFOX_ALLOW_TEST_KEYSTORE=1 # اختبار فقط
bash scripts/verify-qa.sh
```

مفتاح الاختبار ليس مفتاح إصدارك الأصلي. استخدم توقيعك المعتمد لبناء تحديث لنفس الحزمة المثبتة؛ Android لا يقبل تحديثًا بشهادة مختلفة. لا توجد مفاتيح أو mapping أو local.properties أو كاش ضمن المصدر المسلّم.

اختبارات المضيفات المختلفة محلية، تستخدم Activity subclasses بأسماء حزم مختلفة. لا تُعدّ تجربة فعلية على كل تطبيق/هاتف أو على إطار تحميل إنتاجي. النتيجة والبصمات موثّقتان في `EMBEDDED_VALIDATION_AR.md`.
